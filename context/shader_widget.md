# shader_widget.rs

The custom iced `shader::Program`/`Primitive` that owns essentially all rendering and interaction state, independent of `HypercubeApp`. `HypercubeShaderProgram` (per-frame config), `HypercubeShaderState` (persistent: camera, 4D rotation matrix, hover/click/double-click bookkeeping, animation state, the `Hypercube` puzzle state), `HypercubePrimitive` (per-draw snapshot). Mouse/keyboard events are handled here; a `RotateButton` setting assigns one mouse button to camera orbit (+Shift for 4D rotation) and the other to puzzle turn-clicks, so the two never conflict. A turn-click's direction is resolved by `moves::clockwise_sign` to always turn clockwise as viewed along the clicked facet's own rotation axis; Shift reverses it to counterclockwise. Double-click on a face triggers a "center this face" animation via `math::shortest_arc_plane`. A reveal/hide flourish (`AnimatingReveal`) spins the camera 720° in yaw while sticker scale/face gap sweep toward secondary/primary defaults, driven by the same `RedrawRequested`-tick loop as the move/focus animations; camera-drag and turn-click input are ignored while it plays.

`draw()` also builds `HypercubePrimitive::fire_order` under `Theme::Elemental` (empty otherwise): `fire_draw_order` collects the instance indices of `ELEMENTAL_FIRE_KIND` stickers on visible faces and orders them farthest-first, since Fire's pass blends and writes no depth. `FireSticker::is_behind` decides each pair by ray casting: for each of a sticker's 8 real projected corners (`math::transform_sticker_vertices_to_3d`, the same per-vertex transform the vertex shader and hover/click picking use), it casts a ray from the camera eye through that corner and tests it against the other sticker's actual triangle geometry with `ray_casting::ray_sticker_intersection` (prefiltered by `ray_casting::ray_intersects_aabb` against a precomputed `ray_casting::AABB`) - the same exact ray-vs-cube test hover and click picking already use, rather than an approximating scalar key. A nearer hit means the other sticker occludes that corner; a farther hit means the corner is nearer. This is done with both stickers' corners tested against each other, since a size mismatch after the 4D perspective divide can leave every corner of a smaller sticker outside a larger one's silhouette even while they visually overlap; when tested corners disagree - which can happen for two stickers on different tesseract cells whose shared boundary is viewed near-edge-on, since that boundary is no longer a single plane after each cell's own projection - the verdict from whichever corner point is nearest the camera wins. A pair whose corners never land inside each other's geometry (the common case; most fire stickers don't overlap on screen at all) yields no edge, so `topological_draw_order` linearizes only the edges that exist into an order, taking the farthest currently-unblocked sticker at each step (which alone reduces to plain depth order wherever there are no edges) and degrading to depth order for anything caught in a cycle. While a move animation is sweeping a slab the face's cells are no longer the axis-aligned lattice the rest of the frame assumes, so `draw()` passes `lattice_is_aligned: false` and depth alone decides for every pair.

`draw()` also computes `HypercubePrimitive::ui_controls.ground_truth_debug_face` via `ground_truth_debug_face()`, for `Renderer`'s Fire ground-truth debug inset (see `renderer.md`): `None` when the debug toggle is off, the theme isn't `Elemental`, or nothing is currently kind `ELEMENTAL_FIRE_KIND`; otherwise it cycles through every face_id currently holding a Fire sticker, ascending, spending `GROUND_TRUTH_DEBUG_FACE_CYCLE_SECONDS` on each before advancing and looping forever. It's driven by `elapsed_seconds` rather than its own timer, since Elemental's continuous materials already force a redraw every tick.

`HypercubeShaderState.elapsed_seconds` accumulates real wall-clock time across `RedrawRequested` ticks (wrapped modulo 3600), independent of `last_redraw_instant` (which resets to `None` once no animation needs another tick) via its own `last_tick_instant`, and is threaded through `HypercubePrimitive`/`prepare()` into `Renderer::update_instances`. Selecting `Theme::Elemental` forces that tick's `event::Status` to `Captured` even when every other animation is idle, since Elemental's sticker materials animate continuously off `elapsed_seconds` alone and have nothing else to signal that a redraw is still needed.

`HypercubeShaderState` also owns a `rng: fastrand::Rng` and a `random_moves_generation` counter that mirrors `reset_generation`'s mismatch-detection pattern in `Program::update()`: on a mismatch it applies `random_move_count` random legal moves instantly via `Hypercube::apply_random_moves`, bypassing `AnimatingMove` entirely - backing the UI's random-move/Scramble buttons.

A `reset_generation` mismatch also solves the puzzle instantly but animates the 4D orientation back to identity rather than snapping it: `AnimatingReset` decomposes `rotation_4d` (via `math::decompose_so4`) into a pair of unit quaternions at the moment Reset is pressed and slerps both toward identity each tick, recomposing `rotation_4d` (via `math::compose_so4`) - the true geodesic path in `SO(4)`, unlike the single-plane `AnimatingFocus` approach. While it plays, 4D drag rotation, double-click "center this face", and turn-clicks are all no-ops; 3D camera drag is unaffected.

`save_generation`/`load_generation` mismatches drive explicit puzzle save/load, the same generation-counter bridge `reset_generation` uses - necessary because `HypercubeApp` has no direct handle on the live `Hypercube`, which lives only in `HypercubeShaderState`. This module never touches `puzzle_state.rs`/disk itself: on a save mismatch it clones `state.hypercube` and hands it up via `Action::publish(Message::PuzzleReadyToSave(..))` for `HypercubeApp` to persist; on a load mismatch it takes an already-loaded `Hypercube` out of `HypercubeShaderProgram::pending_load` (a `Cell<Option<Hypercube>>`, since `Program::update` only gets `&self`) - populated by `HypercubeApp` calling `puzzle_state::load()` before threading it in - and, if present, replaces `state.hypercube` and clears the same in-flight animation/interaction fields a reset does. A `None` `pending_load` (missing or invalid save file) is a no-op.

A `save_snapshot_generation` mismatch (debug-only Save Snapshot button) follows the same bridge shape but needs no round trip through `HypercubeApp`: `Program::update()` builds a `snapshot::ViewSnapshot` directly from `self`'s per-frame config and `state`'s live puzzle/camera/rotation, stores it in `state.pending_snapshot` (a `Cell<Option<ViewSnapshot>>`, same reason `pending_load` is one), and syncs the counter. `draw()` takes it into `HypercubePrimitive::snapshot_request`; `Primitive::prepare()` - which has `device`/`queue`, unlike `render()` - captures this frame's actual pixels via `Renderer::capture_frame` and calls `snapshot::save` when it's `Some`, so the saved PNG matches what's on screen exactly rather than a separately-reconstructed render.
