# piece.rs

Core domain model. `Piece { position: [i8;4], kinds: [Option<u8>; 4] }`; `position` is a lattice point in `{-1,0,1}^4`, `kinds[axis]` is set only for nonzero axes, naming the opaque sticker kind facing that axis (interpreted only by the active theme's shader). `Hypercube` always holds exactly 81 pieces in a canonical order (`index_of`/`position_of`), so two states can be compared with `assert_eq!` directly — this piece-based model replaced an earlier sticker-based one. `FACET_TABLE` (216 entries, built face-major — 8 contiguous blocks of 27 sharing a `face_id`) and `generate_sticker_instances()` derive per-frame GPU instance data from piece state; the face-major grouping is load-bearing for `renderer.rs`'s per-face draws, not incidental.

`side_for_kind(kind)` is the inverse of `side_kind`/`face_id_for`: given a sticker's kind, the `(axis, sign)` home side it belongs to. Exposed (rather than the private `FACE_AXIS_SIGN` table itself) for `solver` to work out where a piece's stickers "want" to go, without needing index-based lookups.

`FacetGeometry::facet_count()` (2 = face-type, 3 = edge-type, 4 = corner-type) is `1 +` the number of nonzero `local_coords`, mirrored onto each `StickerInstance` as a `facet_count` field so the GPU can classify a facet's piece type too - both feed the first-run tutorial's flash-the-target-pieces highlight and its piece-type input restriction (see `context/shader_widget.md`).
