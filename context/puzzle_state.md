# puzzle_state.rs

Explicit save/load of the puzzle's piece arrangement (`Hypercube`, already `Serialize`/`Deserialize`) to `puzzle_state.json`, sitting alongside `settings.toml` in the same config directory. Mirrors `settings.rs`'s `config_path()`/`load()`/`save()` pattern (same `directories::ProjectDirs` qualifier, `log::warn!` on every failure path, no `Result` propagated to callers) but serializes as JSON via `serde_json`, not TOML: TOML has no null, so `Piece.colors: [Option<Color>; 4]` can't round-trip through `toml` (this was the cause of a "unsupported None format" save failure before the switch). One further deliberate difference from `settings::load()`: `load()` here returns `Option<Hypercube>`, not a value with a default fallback. There's no sensible default for a missing/invalid puzzle state file - silently replacing an in-progress puzzle with a solved one on a failed Load would look like it worked while actually discarding whatever was there, so a missing/invalid file is a true no-op for the caller. Both `save()`/`load()` are called only from `app.rs`, not `shader_widget.rs`: `HypercubeApp` calls `load()` synchronously on `Message::LoadPuzzle` and threads the result into the shader program for it to apply on a `load_generation` mismatch, and calls `save()` on `Message::PuzzleReadyToSave`, which `shader_widget.rs` publishes with a clone of its live `Hypercube` on a `save_generation` mismatch - see `shader_widget.md` and `app.md`.
