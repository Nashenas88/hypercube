# renderer.rs

Owns all wgpu resources (buffers, pipelines for standard/normal/depth/debug/sky/post-process, textures). `render()` picks its sticker pipeline/bind group from `(current_render_mode, current_theme)`: `RenderMode::Standard` dispatches to `classic_pipeline` or `elemental_pipeline` depending on `Theme`, both sharing `main_bind_group_layout`/`main_bind_group`; `Normals`/`Depth` ignore the theme entirely. Under `(Standard, Elemental)`, once that opaque pass ends (dropping its `render_pass` so further ones can open on the same encoder), `render()` walks `self.depth_batch_groups` - one `Vec<DepthBatchGroup>` per batch of `HypercubePrimitive::depth_order` (built by `shader_widget::depth_draw_order`'s topological sort over Fire/Ice/Light/Dirt stickers, turned into GPU draw plans by `update_depth_batches`/`group_depth_batches`), farthest batch first - opening one fresh render pass per batch, since batches must render strictly in order but a batch's own members can draw in any order. A batch's groups partition its stickers by `(kind, face_id)` into one instanced `draw_indexed` each (via `depth_batch_remap`/`vs_main_batched`, so one draw call can cover an arbitrary, non-contiguous subset of stickers), issued Fire-then-Ice-then-Light-then-Dirt purely to minimize pipeline/bind-group switches within the pass. If any group in a batch is Ice, the whole `scene_texture` is first copied to `ice_bg_texture` (outside any pass, since a texture can't be a render target and a sampled input at once), so that batch's Ice groups can read back every farther batch's already-drawn result for their refraction. Fire, Light and Dirt draw through `fire_pipeline`/`light_pipeline`/`dirt_pipeline` - premultiplied `One`/`OneMinusSrcAlpha` blend, depth test on, depth write off, over the same `elemental_shader.wgsl` module and `main_bind_group` as the opaque pass - while Ice draws through `ice_pipeline` (opaque, depth-writing, plus its own second bind group for the background/noise textures). `elemental_shader.wgsl`'s `fs_main` discards `kind == 0` (Ice), `kind == 3` (Fire), `kind == 4` (Dirt) and `kind == 5` (Light) so none of the four is shaded twice by the opaque pass. Not writing depth is what Fire's, Light's and Dirt's back-to-front batch order pays for, and it buys three things: a farther sticker's material still blends through a nearer one's translucent rim, a sticker's edge fades out instead of being cut where it stops claiming depth, and the particles drawn afterward stay visible where they pass behind one - writing depth would also write the wrong value, since the rasterized fragment sits on the cube's front face rather than on the raymarched surface it shades. Unlike Fire's and Light's density-based coverage, Dirt's is a hard 0.0/1.0 from a raymarched SDF hit/miss, but it still needs the same blended, depth-write-off treatment, since its rock box doesn't fill a sticker's own local cube and so leaves real transparent gaps at a facet's edges. Ice instead writes real depth and an opaque result, since there's no blending left for the GPU to do once its shader has already composited the background itself. All four draw after the opaque pass, whose depth they test against, and before the particles, which are additive and so glow over them rather than overwriting them. Once that whole loop ends, `render()` calls `render_ground_truth_debug_inset()` if `current_ground_truth_debug_face` (`set_ground_truth_debug_face`) is set: a second pass that loads `scene_view` (not clearing it) and draws every cell of that one `face_id` - not just Fire ones, and regardless of `visible_faces` - with `classic_pipeline` (opaque, depth-tested), restricted via `set_viewport` to a small `GROUND_TRUTH_DEBUG_INSET_FRACTION`-sized square pinned to `self.bounds`'s corner. It reuses the exact same live vertex/instance/transform buffers the main pass just drew with, so the inset can never drift from what `shader_widget::depth_draw_order` actually scored - the same transform decides the geometry either way; only the viewport differs, remapping the same clip-space output into the smaller rectangle. Its depth-stencil attachment is `debug_inset_depth_view`, a texture dedicated to this pass and resized alongside `depth_texture` - reusing `depth_view` and clearing it again here would erase the main scene's depth values that `render_debug_aabb()` reads back after `composite()`. The same pass then appends `particle_pipeline` draws - one per visible 4D face and populated `kind`, each a sub-range of `particle_ranges[face_id][kind]` (billboard instances of 6 generated vertices each, no vertex or instance buffer) - additively blended with depth test on and depth write off, so particles are hidden by geometry in front of them, glow over geometry behind them, and need no back-to-front sort. Those ranges index into `sticker_order_buffer`, an indirection buffer of sticker indices grouped into contiguous `(face_id, kind)` blocks (`build_sticker_order`/`build_particle_instances`) and rebuilt by `update_sticker_instances` whenever `sticker_generation` changes, since a move can change which kind occupies which face; the vertex shader looks a particle's owning sticker up there instead of dividing its instance index by a shared per-kind budget, so each `kind` can carry its own particle count (`Theme::particles_per_kind`) - though with Dirt (the last kind to gain a material that carries its whole look) now zeroed alongside the rest, that budget is currently `[0; 8]` for every kind under both themes, so this whole apparatus - `particle_pipeline`, `sticker_order_buffer`, `build_sticker_order`/`build_particle_instances` - is presently dormant rather than removed, kept as the mechanism a future particle-emitting kind would reuse. `sticker_order_buffer` is padded with one dummy element when its real content is empty (mirroring `debug_instance_buffer`'s own zero-size-buffer guard), since `create_buffer_init` requires a non-zero-length `contents` slice to produce a bindable buffer. It reuses `classic_pipeline_layout`/`main_bind_group` and simply leaves the bindings it doesn't read unused. Draws the 216 sticker facets per pipeline with up to 8 instanced draw calls, one per 4D `face_id`: each draws a 36-index winding-corrected chunk (`face_index_buffer`, computed by `calculate_indices`) against the matching 27-instance range. This depends on `FACET_TABLE` (`piece.rs`) being built in face-major blocks of 27 — see that table's doc comment. `render()` takes a `visible_faces: &[bool; 8]` (from `math::visible_faces`, `HypercubePrimitive`'s own field, computed in `shader_widget.rs`'s `draw()`) and skips the draw call entirely for any `face_id` it marks invisible — but only outside a move animation: `sticker_instances_for_render` can rotate a moving-layer facet's `face_normal_4d` away from its static `face_id`'s `FACE_CENTERS` direction mid-turn, so `draw()` falls back to "all visible" while `animating_move` is set and lets the vertex shader's own (unchanged) `is_face_visible` cull per-instance instead, same as before this optimization existed. `update_indices`/`update_sticker_instances` are generation-gated: `HypercubeShaderState` tags its cached index/instance buffers with a generation counter (bumped only when the underlying data actually changes — 4D rotation for indices, move animation/`Hypercube` state for instances), carried through `HypercubePrimitive`, so `Renderer` skips the `queue.write_buffer` GPU upload on frames where nothing changed (e.g. a plain 3D camera drag).

`render()` draws into `scene_view`, an offscreen `HDR_FORMAT` (`Rgba16Float`) target rather than iced's own surface - every pipeline above targets it, so a material can write emission past 1.0 without clipping at the display's 8-bit range. `composite()` (called separately, after `render()`) turns that into the final frame: under `Theme::Elemental` it runs `bright_pass_pipeline` (thresholds `scene_view` into half-res `bloom_view_a`) then `blur_h_pipeline`/`blur_v_pipeline` (a separable Gaussian blur ping-ponging `bloom_view_a`/`bloom_view_b`, leaving the result back in `bloom_view_a`); otherwise it clears `bloom_view_a` to black so a stale bloom from an earlier Elemental frame is never added in. Either way a composite pipeline then blits `scene_view` plus `bloom_view_a` into `target` (iced's surface), viewport-restricted to `self.bounds` same as `render()`'s own passes - `composite_tonemapped_pipeline` under `Theme::Elemental`, which applies an ACES curve so emission written above 1.0 keeps its shape, and `composite_pipeline` otherwise, which writes the linear sum through unchanged so Classic is unaffected. The two are built from one closure over the same module and bind group, differing only in fragment entry point. All four post-process pipelines share `post_process.wgsl`'s `vs_fullscreen` (a fullscreen triangle from `@builtin(vertex_index)` alone, no vertex buffer) and read `@builtin(position)` directly for their UV, since only the composite pass's viewport is restricted - the others always cover their entire (freshly resize-tracked) target. `scene_texture`/`bloom_texture_a`/`bloom_texture_b` and their bind groups (`create_hdr_target`/`create_post_process_bind_groups`) are recreated in `resize()` alongside `depth_texture`, at the window's full size and half that respectively; nothing but `composite_pipeline`'s own output format depends on `format`, the real surface format passed into `Renderer::new` - every other pipeline, `debug_pipeline` (AABB) aside, targets `HDR_FORMAT` regardless. `render_debug_aabb()` draws directly onto `target` after `composite()`, so debug AABBs are excluded from bloom and need no HDR treatment.

`render_gizmo()` draws the rotation-axis gizmo (see `shader_widget.md`), immediately after `render_debug_aabb()` and structured identically to it - its own pass straight onto `target` (`LoadOp::Load` for color and depth, depth-tested but not depth-written, alpha-blended, viewport-restricted to `self.bounds`) so it layers over the fully composited frame and is excluded from bloom/tonemap. Unlike `debug_pipeline`'s per-instance AABB cubes (a shared unit-cube vertex buffer plus a `DebugInstance` transform/color storage buffer), the gizmo's ring/marker geometry is already fully resolved to 3D positions on the CPU each frame (`shader_widget::gizmo_ring_vertices`), so `gizmo_pipeline` takes a plain, non-instanced vertex buffer of `GizmoVertex { position, color }` - color rides per-vertex rather than per-instance since ring/marker/axis coloring varies within one draw call - through `gizmo_shader.wgsl`, a trimmed `debug_shader.wgsl` needing only the camera uniform. `update_gizmo()` mirrors `update_debug_instances()`: a reused scratch `Vec` written into a fixed-capacity `gizmo_vertex_buffer` (`GIZMO_VERTEX_CAPACITY`, sized above the two-ring worst case) via `queue.write_buffer`, so neither ever needs per-frame buffer-growth logic. `gizmo_pipeline` disables backface culling (`cull_mode: None`), unlike `debug_pipeline`'s `Back`, since a thin ribbon - unlike a watertight AABB cube - must stay visible from either side as the camera orbits.

`capture_frame()` renders and composites into a scratch `RENDER_ATTACHMENT | COPY_SRC` texture at `target_format` (the real surface format `Renderer::new` was given - kept on `self` since `composite_pipeline`/`composite_tonemapped_pipeline` are fixed to it at pipeline-creation time), then reads it back to CPU-side RGBA8 via the free function `read_texture_rgba8` (row-padding-aware `copy_texture_to_buffer` + `map_async`, blocking the caller). It handles `Bgra8Unorm(Srgb)` via a byte swap and `Rgb10a2Unorm` - a 32-bit-packed 10-bit-per-channel layout some HDR-capable compositors negotiate as the window surface format - via bit unpacking (`A2B10G10R10_UNORM_PACK32`); an unrecognized format logs a warning and assumes raw R,G,B,A byte order rather than silently producing wrong colors. `shader_widget.rs`'s Save Snapshot feature and `renderer::tests`' golden-image tests (`assert_matches_golden`, comparing a fixed deterministic render against a PNG checked into `test_fixtures/golden/`) are the two callers.
