`HypercubeApp` holds only UI-control state (scale/gap sliders, render mode, settings, the reveal toggle's runtime state). Builds a left control panel plus a right `Shader::new(HypercubeShaderProgram)` viewport, with a File/Puzzle/View/Help menu bar (`menu_overlay::bar`, see `menu_overlay.md`/`menu_layout.md`) above them. Contains no 3D/4D logic. The sticker-scale/face-gap sliders sit behind a "Reveal"/"Hide" toggle button, now on the Puzzle menu: pressing it bumps a `reveal_generation` counter (same one-shot generation-counter pattern `reset_generation` uses to reach `HypercubeShaderState`), flips `revealed` immediately, sets `reveal_animating` (disabling the button and manual slider interaction until `shader_widget.rs` publishes `Message::RevealAnimationComplete` once the flourish settles), and records `reveal_animation_started`. While `reveal_animating` is true, a `window::frames()` subscription (see `HypercubeApp::subscription`) feeds `Message::RevealAnimationTick` on every redraw, and `app.rs` interpolates `sticker_scale`/`face_gap` itself (via `crate::animation::ease` and the same `PRIMARY_*`/`SECONDARY_*`/`REVEAL_ANIMATION_DURATION` constants `shader_widget.rs` targets) so the slider thumbs visibly track the 3D flourish - this is a separate, independently-timed interpolation from the shader widget's own `AnimatingReveal`, not values threaded out of it.

The sticker-scale/face-gap panel itself (a `Scrollable` with a hidden scrollbar, wrapping a `mouse_area` that swallows its own wheel-scroll input) is always present in the layout, grouped with the Reveal button and the Animation Duration row into one `spacing(0)` sub-column so no gap is ever inserted or removed around it. Its own leading/trailing blank `Space` margins (`SLIDERS_PANEL_GAP`) stand in for that spacing instead. `reveal_panel_fraction` (updated alongside `sticker_scale`/`face_gap` in the same tick handler, via `panel_progress`'s own faster open/close window) drives the panel's height, linearly interpolated between `SLIDERS_PANEL_CLOSED_HEIGHT` (just the leading margin, reading as one ordinary gap) and `SLIDERS_PANEL_OPEN_HEIGHT` (both margins, both rows, and the gap between them) - `Scrollable` gives its content unconstrained height to lay out against regardless of its own configured height, so the rows never reflow, only the visible window clips.

The Puzzle menu's "1/2/3 Random Moves" and "Scramble" items all send `Message::RandomMoves(count)`, which bumps `random_moves_generation` and stores `count` in `pending_random_move_count` - a payload carried alongside the counter the same way `revealed` accompanies `reveal_generation`, since a bare generation bump can't carry data on its own.

The Puzzle menu's "Reset" item sends `Message::Reset`, which bumps `reset_generation` to reset the 4D orientation only - the puzzle's piece arrangement is untouched; re-triggering Reset/Random Moves/Scramble while a previous one is still animating is harmless, since both handlers in `shader_widget.rs` just restart cleanly from whatever the live state is. Spacer rows between the Reset/Random-Moves-and-Scramble/Reveal groups (`menu_layout::puzzle_items`) target `Message::NoOp` - `overlay::menu::Menu` has no separator concept, so these are inert rows used purely for visual grouping.

`HypercubeApp` owns all `puzzle_state.rs` I/O; `shader_widget.rs` never touches disk. The File menu's Save item sends `Message::SavePuzzle`, bumping `save_generation` (threaded into `HypercubeShaderProgram::new(...)` alongside the other generation counters); `shader_widget.rs` detects the mismatch, clones its live `Hypercube`, and publishes it back as `Message::PuzzleReadyToSave`, which `HypercubeApp` persists via `puzzle_state::save`. Load sends `Message::LoadPuzzle`, which calls `puzzle_state::load()` synchronously and stores the result in `pending_load: Option<Hypercube>`, threaded into the shader program alongside `load_generation` for it to apply on a mismatch. Quit sends `Message::Quit`, returning `iced::exit()`. `about_open` shows a Help modal, and `settings_open` a File > Settings modal (`settings_modal()`, styled like `about_modal()`: Debug Mode/Show Gizmo Ring checkboxes, a Rotate Button `PickList`, a "Show tutorial on launch" checkbox, and a Replay Tutorial button, closed via its own Close button or a backdrop click), both always layered via a constant-shape 6-element `iced::widget::stack` (an inert `Space` placeholder for whichever is closed) rather than conditionally wrapping the content in a `stack` - switching the tree root's shape on toggle would otherwise reset every descendant's widget-tree `State`, including the `Shader` widget's generation counters, causing spurious replays (e.g. the reveal flourish firing again) on every open/close. `subscription()` wires Ctrl+Q/Ctrl+S/Ctrl+O/F1 to Quit/SavePuzzle/LoadPuzzle/OpenAbout, mirroring the File/Help menu items.

Debug Mode and Show Gizmo Ring are persisted `AppSettings` fields (like Rotate Button/Theme, see `settings.md`) rather than plain `HypercubeApp` fields, so they survive a restart; both, plus Rotate Button, live in the Settings modal rather than the left control panel. A "Show Gizmo Ring" checkbox (off by default, unlike the debug-gated checkboxes below) threads `settings.show_gizmo_ring` into `HypercubeShaderProgram::new(...)`, gating whether `shader_widget.rs`'s rotation-axis gizmo ring renders at all during focus/drag/Reset animations (see `shader_widget.md`).

`tutorial_step: Option<usize>` drives a first-run tutorial (`tutorial_modal()`, sixth stack layer): `None` when closed, `Some(i)` for the current step into the `TUTORIAL_STEPS` table (title + body lines per step, covering only the controls - camera orbit, 4D drag, turning a face, focusing a face, Reveal/Puzzle menu - not solving technique). `new_inner()` sets the initial value via `initial_tutorial_step(settings.show_tutorial_on_launch)`, so it opens automatically only when that persisted flag is set. `TutorialNext`/`TutorialBack` step within bounds; `TutorialSkip` and `TutorialFinish` (the last step's "Done" button) both close the tutorial *and* clear `show_tutorial_on_launch` (+ `settings::save`), so dismissing it any way stops it from reopening on the next launch - the Settings modal's checkbox is the only way to re-arm it, and its "Replay Tutorial" button reopens it immediately (`tutorial_step = Some(0)`) regardless of that flag.

The stack's last layer is a debug-only FPS counter: while `debug_mode` is on, `subscription()` adds a `window::frames()` subscription mapped to `Message::FpsTick`, and each tick updates `fps` (an exponential moving average over the delta from `last_fps_frame`, reset whenever `debug_mode` is (re-)enabled so a stale timestamp gap can't produce one bogus reading). `view()` renders `fps` as plain `iced::widget::text`, right/top-aligned over the viewport with no `mouse_area`/`opaque` wrapping (unlike the About modal) so it never intercepts clicks meant for the cube underneath - an inert `Space` swaps in for this layer whenever `debug_mode` is off.

**Solving.** The Puzzle menu's second item is "Solve", or "Stop Solving" while one plays (`solve_button_label`). `Message::Solve` (ignored while `solving`) sets `solve_command = SolveCommand::Start`, bumps `solve_command_generation` and sets `solving`; `Message::StopSolving` - also sent by Esc, gated here since subscription closures can't capture state - does the same with `Stop` and clears `solving`. Reset, Random Moves and a successful Load just clear `solving` locally (`stop_solving_locally`), since `shader_widget.rs` cancels playback itself on those. `SolveProgress`/`SolveEnded` from `shader_widget.rs` apply only while `solving` and only when their `generation` matches, so late messages from a cancelled run are dropped. `SolveEnded` posts `solve_notice` ("Solved in 1,204 moves", "Already solved", or "Can't solve: …" with the `SolveError`'s `Display`), which a `window::frames()` subscription (`Message::SolveNoticeTick`) expires after `SOLVE_NOTICE_DURATION`. The stack's second layer (`solve_layer`, shaped like the FPS layer but bottom-right) shows `solve_overlay_text`: "Solving: orienting 3-sticker pieces · move 812 / 1,904" while solving (`format_count` adds the thousands separators), the notice afterwards, an inert `Space` otherwise. The About modal credits the solver's source (NdSolve by Don Hatch, from Magic Cube 4D by Melinda Green & Don Hatch, superliminal.com/cube/cube.htm) and mentions Esc.

**About dialog licensing.** Beyond the control scheme, `about_modal()` lists every license/attribution obligation the project carries, mirroring `README.md`'s License section: the project's own MIT/Apache-2.0 dual license, the NdSolve/Magic Cube 4D solver port, the Water/Ice/Lightning shader ports (each with its source and, where one is stated, its Creative Commons license - Lightning has none), and the CC0 skybox. Each entry is built by `license_entry` (description text plus a `Row` of link buttons) and each link is a `link_button` - a `Button` wrapping an underlined `text::Rich` span (plain `Text`/`Style` has no underline; `Rich`'s `Span::underline` does) and styled via `link_button_style`. `extended_palette().primary.base.color` (a raw, unvetted accent color) isn't guaranteed to read against any particular surface, so `link_button_style` instead runs it through `iced::theme::palette::readable` against the popup's own background (`background.weak.color`, matching its `container::rounded_box` style) to get a legible base link color, then `palette::deviate` for a visibly distinct, still-legible hover shade - so the link reads as clickable through color and underline together, in every built-in theme. Pressing it sends `Message::OpenUrl(url)`, handled in `update()` by calling `open::that(url)` (the `open` crate) and logging via `log::warn!` on failure rather than panicking, since opening a browser is best-effort. The popup itself is wrapped in a `scrollable` with a capped `max_height` now that its content no longer fits one screen unscrolled.
